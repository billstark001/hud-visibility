# Multi-Version Loader Example Mod

A minimal Minecraft mod template using one set of sources for **Fabric** and **NeoForge**.
The base Java package is `com.example.mod`, the mod ID is `example_mod`, and the mod version is `0.1.0`.
The example mod stays at `0.1.0`; the changelog tracks the template's development separately.
The main menu includes a **Template Info** button. It shows the compiled Minecraft target, actual game version,
the numeric `MC_VERSION` macro, and a PASS/FAIL version check. Click **Back** to return to the menu.
`TemplateDemo.java` uses real `#if` branches for the version-name and screen-navigation APIs that changed between
these releases. This small feature can be removed when you start implementing your mod.

## Supported targets

| Minecraft | Java | Fabric API | NeoForge |
| --- | --- | --- | --- |
| 1.21.1 | 21 | 0.116.17+1.21.1 | 21.1.262 |
| 1.21.11 | 21 | 0.141.4+1.21.11 | 21.11.44 |
| 26.2 | 25 | 0.152.2+26.2 | 26.2.0.37-beta |
| 26.3 | 25 | 0.161.0+26.3 | 26.3.0.6-beta |

Each Minecraft/loader pair produces a separate JAR. Fabric 1.21.x uses official Mojang mappings and Loom remapping;
26.x uses the unobfuscated game with Loom. NeoForge 26.x versions in this template are beta releases.
The metadata deliberately requires the exact Minecraft target; widen a range only after testing it.
Fabric Loader is pinned to 0.19.3 and Fabric API is a required runtime dependency.
NeoForge builds have no third-party mod dependencies.

## Build and verify

Run Gradle with JDK 21 or newer; JDK 25 is recommended. The Gradle toolchain resolver can download missing JDKs
21 and 25. The wrapper and pinned plugin versions are included.

```powershell
.\gradlew.bat buildAll --no-parallel
.\gradlew.bat verifyArtifacts --no-parallel
.\gradlew.bat testAll
.\gradlew.bat collectArtifacts --no-parallel
```

On Linux/macOS use `./gradlew`. Individual builds use paths such as
`:versions:fabric-1.21.1:build` and `:versions:neoforge-26.3:build`.

`buildAll` builds all eight targets. JARs and source JARs are written to
`versions/<loader>-<minecraft>/build/libs/`.
`verifyArtifacts` builds and checks all eight distributable JARs for metadata, entrypoints, Mixin configuration,
icon, license, and the correct Java bytecode level. `collectArtifacts` verifies and collects only the eight
distributable JARs in `build/distributions/`; it does not publish anything.
Windows users can also run `.\scripts\build-distributions.ps1`.
`.\scripts\build-modrinth.ps1` builds and verifies the same eight upload JARs into `build/modrinth/`.
Use `-SkipBuild` to validate and collect existing JARs. This script does not upload or publish anything.

`testAll` runs the JUnit 5 module at `tests/unit`. Its test directory starts empty: add loader-neutral tests
under `tests/unit/src/test/java`. The unit module compiles only JDK-only code in `src/main/java`;
if shared code acquires game dependencies or preprocessor directives, adjust that module accordingly.

## Source layout

- `src/main/java/com/example/mod`: shared initialization and loader-neutral code, safe on both physical sides.
- `src/client/java/com/example/mod/client`: client initialization, invoked only by client entrypoints.
- `src/fabric` and `src/neoforge`: loader adapters and their metadata.
- `src/main/resources`: shared resources, a placeholder icon, and the client Mixin configuration.
- `gradle/targets.gradle`: the single source of target versions, dependencies, Java levels, and preprocessor values.
- `gradle/common-target.gradle`: source sets, resource expansion, Java toolchains, license packaging, and Maven publication configuration.
- `gradle/fabric-target.gradle` and `gradle/neoforge-target.gradle`: loader-specific builds and development runs.

The `versions/` projects are generated by settings and do not need checked-in build scripts.
Keep client-only game imports in the client sources and call them only from the client entrypoints.
The NeoForge client adapter is guarded with `@Mod(..., dist = Dist.CLIENT)`; Fabric uses its `client` entrypoint.

## Customize the template

1. Edit `gradle.properties`: set `mod_id`, `mod_name`, `mod_description`, `mod_author`, `mod_group`,
   `mod_version`, and `archives_base_name`.
2. Rename Java packages/directories and update `ExampleMod.MOD_ID`. Metadata entrypoint packages follow
   `mod_group`; update the entrypoint class names in the metadata and artifact check if you rename those classes.
3. Move `src/main/resources/assets/example_mod/` to match your mod ID. Replace the placeholder icon;
   its editable SVG source is included beside the PNG.
4. Add Mixins under your package's `mixin` directory and register their class names in
   `src/main/resources/example_mod.mixins.json`. The build renames that file to match `mod_id`.
5. Update this README, the distribution description, changelog, and license notices for your project.
   Preserve the existing MIT copyright notice for the reused infrastructure.

Metadata is expanded from the Gradle properties. Escape quotes/backslashes when putting them into values used
by JSON or TOML. No project URLs, publishing credentials, or remote Git repository are configured.

## Shared sources and preprocessing

All eight targets use the [Manifold preprocessor](https://github.com/manifold-systems/manifold/tree/master/manifold-deps-parent/manifold-preprocessor).
It runs only inside javac and is not required or bundled at runtime.
`MC_VERSION` is `major * 10000 + minor * 100 + patch`:

| Minecraft | MC_VERSION |
| --- | --- |
| 1.21.1 | 12101 |
| 1.21.11 | 12111 |
| 26.2 | 260200 |
| 26.3 | 260300 |

`src/client/java/com/example/mod/client/TemplateDemo.java` demonstrates four target-specific constant branches,
`WorldVersion.getName()` versus `name()`, and `Minecraft.setScreen()` versus `Minecraft.gui.setScreen()`.
For other APIs that differ across versions, use directives in game-dependent sources, for example:

```java
#if MC_VERSION >= 260200
// Code compiled only for Minecraft 26.2 and newer.
#else
// Code compiled for the 1.21.x targets.
#endif
```

Source JARs preserve these directives. In IntelliJ IDEA, install the Manifold plugin for directive-aware editing
and delegate builds to Gradle.

## Development runs

```powershell
.\gradlew.bat :versions:fabric-1.21.1:runClient
.\gradlew.bat :versions:neoforge-26.3:runClient
.\gradlew.bat :versions:fabric-1.21.1:runServer
.\gradlew.bat :versions:neoforge-26.3:runServer
.\gradlew.bat syncIdeaRunConfigurations
```

Each loader/version has its own `run/<loader>-<minecraft>/` client directory and a separate
`run/<loader>-<minecraft>-server/` server directory. Follow Minecraft's EULA prompt when starting a server.
Gradle generates IDE run configurations; machine-specific IDE files are ignored.
The 26.3 client configurations include the stack-shadow and internal-misc export JVM arguments listed in
Minecraft's vanilla launcher manifest.

On Windows, `localNeoForgeSmoke` or `.\scripts\run-local-neoforge-smoke.ps1` launches each graphical NeoForge client,
checks the shared initializer log and sound-engine startup, then terminates that client's process tree.
Run this explicitly in a graphical desktop session. It does not test gameplay.

To exercise the demo on all eight graphical clients, run `.\scripts\run-local-client-smoke.ps1` directly
in PowerShell. For each client, open **Template Info**, verify **Version check: PASS**, click **Back**, and quit.
The script requires the correct compiled/runtime version, successful return to the menu, and a clean exit;
it records logs and `results.json` in `build/client-smoke/`. Optional `-Loader fabric` and
`-MinecraftVersion 1.21.1` arguments select a subset. Screenshots can be saved in that directory's `screenshots/` folder.
Use `-VerifyExisting` to re-check the saved logs and exit statuses without launching the games again.
The checker reads both the game log and captured stdout/stderr because `System.Logger` can use JUL's console output.

## CI and distribution

The reusable CI workflow runs unit tests and verifies all eight builds. The manual release-bundle workflow
builds and uploads a workflow artifact. Neither workflow publishes to GitHub Releases or Modrinth.
The Maven publication definition supports local development with each target's `publishToMavenLocal` task;
no remote Maven publishing repository is configured.
